# Двухслойная проверка пересортов

Пересорты собираются в два шага.

1. **Детерминированный слой** (`app/core/resort.py`). Правила из `docs/06-resort-rules.md`:
   бренд, схожесть имени, покрытие суммы, ворота по цене, жадный подбор.
   Этот слой решает всё сам и работает без модели.
2. **Второй слой** — на выбор:
   - локальная логистическая регрессия (`app/core/verify.py`);
   - полноценная языковая модель через OpenRouter (`app/core/judge.py`),
     при включённых эмбеддингах — в связке с ними.
   Второй слой не создаёт новых пар: он судит кандидатов слоя 1.

Режим выбирается в интерфейсе на странице загрузки: «Только детерминированная
логика», «Логика + нейросеть» или «Логика + LLM (OpenRouter)». Переменная
окружения `VERIFY_MODE` (`off`, `model`, `llm`) задаёт значение по умолчанию.

## Влияние детерминированной логики (0…100%)

Поле «Влияние детерминированной логики, %» на странице загрузки задаёт
`logic_weight` (0…1 внутри кода). Значение по умолчанию настраивается на
`/training`, запоминается по токену сверки и переживает пересборку файла.

Вес действует **только при включённом втором слое**. Без него в журнал
пишется строка о том, что вес не применяется: решать больше некому.

| Значение | Что происходит |
|---|---|
| 100% | как раньше: ворота по бренду и цене отсеивают кандидатов, оценка детерминированная, модель лишь двигает её (`VERIFY_WEIGHT`) и может пару снять |
| 1…99% | ворота мягкие, итог — `w * оценка логики + (1 - w) * 2 * порог * шанс модели` |
| 0% | решает только второй слой: ворота ничего не отсеивают, пара проходит порог ровно при шансе модели выше 0.5 |

Это и есть проверка «насколько хорошо модель решает сама по себе»:
при 0% детерминированная оценка в итог не входит вовсе.

Два важных следствия:

- **Скорость.** При весе меньше 100% детерминированная оценка считается
  для всех пар «излишек × недостача» внутри группы, а не только для
  прошедших ворота. На больших складах сверка идёт заметно дольше, а в
  режиме LLM ещё и дороже.
- **Молчание модели.** Если второй слой не ответил (`Verdict.known=False`:
  сеть, ключ, предел запросов), пара решается логикой, а пара, не прошедшая
  ворота, отбрасывается. Так сбой сервиса не превращает сверку в случайность.

## Локальная модель (`verify_mode=model`)

Модель — логистическая регрессия на 16 признаках пары «плюс ↔ минус»:

```
similarity, first_word, two_words, three_words, token_jaccard, prefix_ratio,
digits_same, digits_differ, price_close, price_ratio, covers, qty_equal,
row_close, len_ratio, embed_cos, embed_known
```

По вероятности `p` принимается одно из трёх решений:

| Вероятность | Решение |
|---|---|
| `p < VERIFY_REJECT` (0.05) | пара снимается, строки идут в излишек/недостачу |
| `VERIFY_GRAY_LOW ≤ p ≤ VERIFY_GRAY_HIGH` (0.35…0.55) | пара уходит в «Спорные пересорты» на ручной ответ |
| иначе | пара принимается, мнение модели добавляется к оценке с весом `VERIFY_WEIGHT` (0.3) |

Пороги намеренно осторожные. На ручных образцах («Охта», «Балтийская») модель
переносится между складами слабо: точность пары на чужом файле ≈ 0.73.
Поэтому при этих значениях качество итогового разбора не падает
(Охта 37/37 строк, Балтийская 111/126 — как без модели), а модель работает
как фильтр внимания: 1 спорная пара на Охте и 31 на Балтийской.
Агрессивные пороги (`VERIFY_REJECT = 0.2…0.35`) в тестах ломали верные пары,
поэтому по умолчанию не используются.

## LLM как второй слой (`verify_mode=llm`)

Модуль `app/core/judge.py`, класс `LlmJudge`.

- Запрос: `POST https://openrouter.ai/api/v1/chat/completions`, сеть — только
  `urllib` из стандартной библиотеки. Модель по умолчанию —
  `openai/gpt-4o-mini`, меняется на `/training`.
- В подсказку по каждой паре уходят **имена товаров, цены и количества**.
  Если эмбеддинги имён включены, добавляется строка «близость имён по
  эмбеддингам» — это и есть связка LLM с эмбеддинг-моделью.
- Ответ строго в виде `{"answers": [{"id": 1, "p": 0.9}]}`; пояснения вокруг
  JSON допускаются и отбрасываются при разборе.
- Пары идут пачками (`judge_batch`), лучшие кандидаты слоя 1 — первыми,
  чтобы при исчерпании пределов судились самые похожие пары.
- Ответы кэшируются **по нормализованным именам пары**, а не по номерам
  строк: пересборка того же файла новых трат почти не даёт.
- Пределы трат: `judge_max_pairs` — на файл, `judge_max_requests` — на
  процесс службы. По исчерпании остальные пары решает логика.
- Любая ошибка сети, ключа или разбора не роняет сверку: пара получает
  `Verdict.known=False` и решается логикой.
- Кнопка «Проверить ключ» задаёт одну пробную пару (Мальборо/Marlboro) и
  общий кэш судьи не трогает.

**Предупреждения.** Это внешний сервис: имена товаров, цены и количества
уходят за пределы сервера, каждый запрос тратит баланс ключа, а сверка идёт
медленнее, чем на логике. По умолчанию режим выключен.

## Режим обучения в интерфейсе

Страница `/training`:

1. **Загрузить ручной образец** — готовая сверка .xlsx, проверенная человеком.
   Зелёные блоки читаются как подтверждённые пересорты, остальные похожие пары —
   как отрицательные примеры. Сам файл не сохраняется: в базу пишутся только
   числовые признаки пар (`data/train-samples.jsonl`).
2. **Обучить заново** — пересчитывает модель на всех накопленных примерах и
   сохраняет её в `data/verifier.json`. Показывает точность на обучении и на
   отложенном файле-источнике (если источников больше одного).
3. **Эмбеддинги имён** — выбор провайдера, ключ, модель и предел запросов
   (см. раздел ниже), кнопки «Проверить ключ» и «Удалить ключ».
4. **LLM как второй слой** — ключ OpenRouter, модель, адрес, ожидание,
   повторы, размер пачки, пределы пар и запросов, влияние логики по
   умолчанию; кнопки «Проверить ключ» и «Удалить ключ».
5. **Очистить базу примеров** — удаляет примеры, обученная модель остаётся.

Кроме этого, каждый ответ в разделе «Спорные пересорты» на странице результата
сразу становится примером: ответили «пересорт» — положительный, «не пересорт» —
отрицательный. Так модель улучшается от обычной работы, без отдельной разметки.

В репозитории есть стартовая модель, обученная на двух ручных образцах
(480 пар, 198 из них — пересорты).

## Ограничения сервера (1 ядро, 1 ГБ)

- Модель — чистый Python, без numpy/sklearn/torch. Файл модели — несколько КБ.
- Модель читается один раз и кэшируется по пути, времени изменения файла и
  настройкам эмбеддингов; на файл сверки приходится один вызов `load_verifier`.
- Оценка одной пары — 16 умножений, то есть тысячи пар в секунду.
- Обучение (300 эпох, десятки тысяч примеров) — секунды в одном потоке,
  память — десятки МБ. Ограничитель `TRAIN_MAX_SAMPLES` (60000) не даёт базе расти бесконечно.
- Эмбеддинги имён (`app/core/embed.py`) по умолчанию выключены
  (`EMBED_ENABLED=false`) и загружаются лениво, с дисковым кэшем векторов.
  Локальный провайдер (ONNX rubert-tiny2 int8, ~30 МБ) работает в один поток
  (`intra_op_num_threads=1`); включать только при свободной памяти.
  Сетевой провайдер память не тратит, но требует сети и баланса ключа.
  Без `onnxruntime` и без ключа приложение работает как обычно.
- Режим `llm` памяти почти не тратит (запросы по сети), но время сверки
  зависит от сервиса, а траты — от числа пар.
- Локальная LLM на этом сервере не поднимается: 1 ГБ памяти недостаточно.

| `VERIFIER_MODEL_PATH` | `data/verifier.json` | файл модели |
| `TRAIN_STORE_PATH` | `data/train-samples.jsonl` | база примеров |

| `EMBED_API_URL` | `https://openrouter.ai/api/v1/embeddings` | адрес сетевого сервиса |
| `EMBED_TIMEOUT` | `20` | ожидание ответа, секунд |
| `EMBED_RETRIES` | `2` | повторы при обрыве связи |

| `EMBED_CACHE_PATH` | `data/embed-cache.json` | кэш векторов |
| `EMBED_CACHE_LIMIT` | `20000` | предел размера кэша |
| `JUDGE_MODEL` | `openai/gpt-4o-mini` | модель LLM-судьи |
| `JUDGE_API_URL` | `https://openrouter.ai/api/v1/chat/completions` | адрес чата |

`judge_api_key` задаются только в интерфейсе и хранятся в `runtime.json`.
Из окружения они не читаются.

## Эмбеддинги имён (необязательно)

Строковая схожесть не понимает, что «Мальборо» и «Marlboro» — один бренд.
Это закрывает эмбеддинг-модель: косинус между векторами имён идёт в модель
одним признаком (`embed_cos`), а не отдельным решающим правилом. В режиме
`llm` тот же косинус уходит в подсказку языковой модели.

Провайдера выбирает человек на странице `/training`, карточка «Эмбеддинги имён».

### Провайдер `local` — файл ONNX на сервере

Работает без интернета и бесплатно, но требует памяти и файлов модели:

```bash
pip install -r requirements-ml.txt
python scripts/export_embed_model.py   # нужен доступ в интернет и ~1 ГБ свободного диска
```

Файлы готовятся не на VPS, а на машине помощнее, и кладутся в `models/`.

### Провайдер `openrouter` — векторы по сети

- Запрос: `POST https://openrouter.ai/api/v1/embeddings`, тело
  `{"model": "…", "input": ["имя 1", "имя 2"]}`, ответ — `data[].embedding`
  (формат, совместимый с OpenAI). Сеть — только `urllib` из стандартной
  библиотеки, новых зависимостей нет.
- Ключ вводится только в интерфейсе, показывается хвостом (`mask_key`),
  удаляется кнопкой «Удалить ключ».
- Кнопка «Проверить ключ» (`embed.check_remote`) делает один короткий запрос
  и не трогает дисковый кэш.
- На пару имён уходит один запрос, известные имена берутся из кэша.
  `EMBED_MAX_REQUESTS` ограничивает траты: когда предел исчерпан, сверка
  спокойно идёт без эмбеддингов.
- Любая ошибка сети или ключа — молчаливый отказ: признак просто не
  учитывается, сверка не падает.
- Важно помнить: имена товаров уходят во внешний сервис и тратят баланс
  ключа. По умолчанию провайдер — `local`, сетевой включается вручную.

### Общее для обоих провайдеров

- Ключ дискового кэша содержит провайдера и модель (`local|имя`,
  `openrouter:модель|имя`), поэтому векторы разных моделей не перемешиваются.
  Записи старого кэша (без префикса) не подхватываются и просто
  пересчитаются — вреда от этого нет.
- После смены настроек провайдер в памяти забывается (`forget_embedder`),
  перезапуск службы не нужен.
- Признаки `embed_cos` и `embed_known` начинают работать сразу, но веса
  у них появятся только после переобучения модели на `/training`.
