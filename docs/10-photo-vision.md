# Распознавание фото плюсующего товара

Ревизоры присылают на почту фото товара, который оказался в излишке.
Модуль `app/core/vision.py` и страница «Фото товара» помогают привязать
снимок к строке сверки. Решение всегда за человеком: в файл сверки
распознавание ничего не пишет.

## Как это работает

1. Файл сверки уже разобран, гроздья построены, страница результата открыта.
2. Кандидатами становятся **только строки с излишком** (`F > 0`), самые
   крупные первыми, не больше заданного числа строк.
3. Снимок уходит в хранилище файлов GigaChat, затем идентификатор файла и
   список позиций — одним запросом на генерацию.
4. Модель возвращает JSON: прочитанный с упаковки текст, до трёх номеров
   строк и короткое замечание.
5. Номера строк проверяются по списку. Выдумала строку — ответ отбрасывается,
   и подбор делается по прочитанному тексту через `resort.similarity`.
6. Человек отвечает по карточке снимка: «Да», выбор товара из списка или
   «Не товар». Ответ ложится в `data/vision-samples.jsonl` — по нему потом
   видно точность на своих фото. Подтверждение снимает с этой строки
   пометку «нет фото».

Количество штук по фото не считается никогда: количество берётся из сверки.

## Карточки снимков: «Да», выбор товара и «Не товар»

На странице «Фото товара» первым делом идёт сетка карточек — три
колонки и столько рядов, сколько нужно. В сетке **все снимки из
архива выбранной сверки** (письма, сошедшиеся по складу), а не
только те, где модель нашла строку. Карточка — сама фотография,
под ней предложенная строка и две кнопки.

Кнопка «Нет» никуда не отправляет ответ: она открывает
**выпадающий список плюсующих товаров сверки** (правка владельца
от 16.09.2026). Список — тот же, что уходит модели: строки с
излишком, крупные первыми, в виде «Строка 42 — имя товара (3 шт.)».
Первым пунктом идёт «Не товар».

| Ответ | Сверка | Архив письма |
| --- | --- | --- |
| «Да» | подтверждается строка, предложенная моделью: пометка «нет фото» с неё снимается | файл получает имя узнанного товара |
| товар из списка | подтверждается выбранная руками строка, пометка «нет фото» с неё снимается | файл получает имя выбранного товара |
| «Не товар» | ничего не подтверждается, пометка «нет фото» остаётся; строка, которую предложила модель, из подтверждённых убирается | **имя снимка не меняется: остаётся ровно таким, каким пришло в письме** |

«Не товар» не трогает `Photo.title` вовсе: `mail_archive.entry_name`
без него берёт собственное имя вложения. Стирать заголовок тоже
нельзя — тогда из имени файла ушло бы то, что уже узнали раньше.

Клик по кнопке не перезагружает страницу: `app/static/photos.js`
отправляет форму на `POST /vision/answer` (решение `yes` либо
`pick` с номером строки, ноль — «Не товар»), получает JSON
(`{ok, state, message}`) и сворачивает карточку на месте: остаются
имя файла и итог ответа. Без JavaScript список показан сразу и
уходит обычным POST, так что работа не встаёт.

Ответы по карточкам живут в памяти сверки (`Job.photo_answers`,
ключ — `уид письма/имя файла`), поэтому пересборка файла их не
теряет. Карточки и список товаров собирает
`app/services/photo_cards.py` (`cards()`, `options()`), снимок
отдаётся тем же маршрутом, что и в разделе почты
(`GET /mail/photo/{uid}/{name}`). Раздел «Что распознано» ниже
остался только для фото, загруженных на странице руками: в архиве
письма их нет, карточкой они не показываются.

## Пометка «нет фото» в файле

В сверке отмечается не тот товар, по которому фото есть, а тот, по которому
его нет: в столбец 12 (`L`) каждой плюсующей строки (`F > 0`) без
подтверждённого снимка пишется «нет фото». Если в ячейке уже есть текст
(например, заявка реестра), пометка дописывается через запятую. Подтверждение
снимка убирает пометку с его строки, остальные плюсующие строки остаются
отмеченными. Ответ «Не товар» возвращает пометку на предложенную строку.

Пометки ставит `app/core/photo_mark.py` (`apply()`) **после каждой сборки
файла**: и при загрузке сверки, и при любой пересборке от исходника
(подтверждение спорных пар, ручные поля, заявки реестра). Раньше пометка
ставилась один раз, в момент подтверждения фото, и следующая пересборка её
стирала — комментарии по фото не доходили до скачанного файла.

Строки с подтверждённым фото живут в памяти веб-слоя (`PHOTO_ROWS` по токену
сверки), поэтому пересборка их не теряет. Перезапуск службы это состояние
стирает: после перезапуска сверку надо загрузить заново. После любого ответа
по фото файл нужно скачать заново.

## Почему GigaChat

GigaChat (Сбер) доступен из России без обходных путей, умеет работать с
изображениями, у версии для физических лиц есть бесплатные токены.
Google Gemini и другие зарубежные службы из России недоступны, поэтому в
качестве провайдера они не используются.

Сетевая часть написана на `urllib` из стандартной библиотеки: новых
зависимостей нет. Проверка сертификата по умолчанию отключена — у Сбера
цепочка Минцифры, которой в системном хранилище обычно нет. Если сертификаты
Минцифры на сервер установлены, в `data/runtime.json` можно поставить
`"vision_verify_ssl": true`.

Авторизация двухшаговая:

1. Ключ авторизации (строка Basic из личного кабинета) меняется на токен
   доступа запросом `POST /api/v2/oauth`.
2. Токен живёт 30 минут и держится в памяти процесса, обновляется с запасом.

Версия API (`scope`) подбирается сама: сначала версия для физических лиц,
затем B2B и корпоративная. Сработавшая версия запоминается в настройках,
чтобы в следующий раз не перебирать.

## Настройка через интерфейс

Всё задаётся на странице «Фото товара» и хранится в `data/runtime.json`.
Править `.env` и перезапускать службу не нужно, обновление по OTA настройки
не затирает.

| Настройка | По умолчанию | Зачем |
| --- | --- | --- |
| Включить распознавание | выключено | Общий переключатель |
| Ключ авторизации | пусто | Строка Basic из личного кабинета GigaChat |
| Модель | `GigaChat-2` | Модель с поддержкой изображений |
| Строк-излишков в запросе | 40 | Короткий список отвечает точнее |
| Предельный размер снимка | 8 МБ | Телефонное фото обычно меньше |
| Ожидание ответа | 60 с | Таймаут запроса |
| Повторов при сбое | 2 | Только на 429 и сбои службы |
| Пауза между снимками | 4 с | Предел обращений в минуту |
| Порог подбора по тексту | 0,55 | Ниже — строка не предлагается |
| Предел кеша | 2000 снимков | Одно фото не уходит в API дважды |

Ключ хранится на сервере и на странице показывается только хвостом
(`…abcd`). Пустое поле при сохранении означает «оставить как было».
Кнопка «Удалить ключ» стирает его из настроек. Папка `data/` не попадает в
Git.

## Порядок включения

1. Получить ключ авторизации в личном кабинете GigaChat.
2. На странице «Фото товара» включить распознавание, вставить ключ и
   сохранить настройки.
3. Нажать «Проверить связь»: короткий запрос без картинки покажет, что ключ,
   версия API и модель рабочие.
4. Загрузить сверку на главной странице, вернуться сюда и ответить по
   карточкам снимков: «Да», товар из списка или «Не товар». Свои фото
   можно приложить руками: одно фото — один товар.

## Чего ждать

Это подсказчик, а не автономный ИИ. Хорошо работает, когда на фото читается
бренд и линейка; хуже — когда снимок смазан, товар без упаковки или в сверке
несколько близких вкусов одного бренда. Точность имеет смысл считать по
собственной базе ответов: сколько раз верхний кандидат оказался тем самым.

## Отказы

Модуль всегда возвращает результат с полем ошибки, а не исключение. Нет
ключа, нет сети, кончились токены, битый ответ — страница открывается,
сверка и выгрузка файла работают как раньше. Если файл сверки не открылся
для пометки, ответ человека всё равно сохраняется, а причина пишется в
журнал службы и на страницу.
