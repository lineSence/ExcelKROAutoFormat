# Правила: настройки и состояние (`CFG-*`)

Код — `app/config.py`, `app/core/runtime.py`, `app/web/routers/*`,
`deploy/.env.example`. Подробности интерфейса — `docs/13-ui-and-settings.md`.

## `[CFG-UI-FIRST]` Пользовательские настройки — только через интерфейс

Зрелость: core · Дата: 2026-09-16 · Источник: решение владельца

Пороги, режимы проверки, ячейки шапки, ключи моделей, почта,
расписание — всё, что меняет ревизор, настраивается страницами
настроек и хранится в `runtime.json`. Правка файлов вручную и
перезапуск службы не должны требоваться ни для одной такой
настройки. Нарушение = регрессия.

## `[CFG-TWO-LAYERS]` Админские настройки — окружение, пользовательские — интерфейс

Зрелость: core · Дата: 2026-09-16 · Источник: решение владельца

Два слоя разделены жёстко:

- **Админские** (`Settings` в `app/config.py`): адрес и порт, логин и
  пароль веб-доступа, пределы загрузки, каталоги, `RESULT_TTL_MINUTES`.
  Задаются переменными окружения при развёртывании, читаются один
  раз на старте.
- **Пользовательские** (`runtime.json`): всё остальное. Из окружения не
  читаются никогда — особенно ключи моделей, чтобы в интерфейсе
  не возникало «призрачного» значения, которое нельзя стереть.

Формулировка «`.env` не используется» из старого контекста отменена
этим правилом: `.env` — законный способ задать админский слой и
только его.

## `[ENV-SYNC]` `deploy/.env.example` сверяется с `Settings`

Зрелость: validated · Дата: 2026-09-16 · Источник: аудит 2026-09-16

Пример окружения — часть админского слоя, поэтому его ключи и
дефолты не должны расходиться с `Settings`. Правка одного из двух
файлов без второго — регрессия, проверяется тестом.

При споре истина — за тем файлом, который правили позже.
Расхождения на 2026-09-16 (`app/config.py` от 15.09 14:20 позже
`deploy/.env.example` от 15.09 12:52, значит истина в коде):

| Ключ | `Settings` (истина) | `.env.example` (подлежит правке) |
| --- | --- | --- |
| `REFS_CELL_REASON` | `C6` | `C5` |
| `REFS_CELL_ADMIN` | `L3` | `L2` |
| `REFS_CELL_CHECKER` | `""` | `L3` |
| `REFS_CELL_AUDITORS` | `L5` | `L4` |
| `TMP_DIR` | `/tmp/excelkro` | `/var/lib/excelkro/work` |

Кроме того, в примере нет `VERIFY_*`, `JUDGE_*`, `EMBED_*`, `TRAIN_*` —
это ожидаемо, потому что они из пользовательского слоя
(`[CFG-TWO-LAYERS]`) и в окружении их быть не должно.

## `[CFG-STATE-PATH]` Путь для `runtime.json` выбирается по очереди

Зрелость: validated · Дата: 2026-09-16 · Источник: `app/core/runtime.py`

`data/runtime.json` в корне → `STATE_DIRECTORY` от systemd →
`/var/lib/excelkro/data` → временный каталог. На сервере корень
перезаписывается обновлением, поэтому состояние должно лежать в
`/var/lib/excelkro`. Новое состояние получает путь только через эту
же функцию, а не своим вычислением.

## `[CFG-FIELDS]` Поле в интерфейсе — запись в `FIELDS`

Зрелость: validated · Дата: 2026-09-16 · Источник: `app/core/runtime.py`

`runtime.FIELDS = EMBED_FIELDS + JUDGE_FIELDS` и т.д.: новая настройка
обязательно попадает в список полей, иначе она молча теряется
при сохранении. Исключение: почтовые настройки живут в
`mail.DEFAULTS`/`mail.KINDS` и сознательно не входят в `FIELDS`.

## `[CFG-EMPTY-KEEPS]` Пустое поле значит «оставить как было»

Зрелость: validated · Дата: 2026-09-16 · Источник: `app/web/forms.py`

Ключи и пароли показываются замаскированными (`vision.mask_key`,
`embed.mask_key`, `mail.mask_secret`), поэтому пустое поле никогда не
стирает секрет. Для удаления есть отдельные кнопки
(`…/key/clear`, `/mail/password/clear`). Новый секрет добавляется
сразу с маской и кнопкой очистки.
