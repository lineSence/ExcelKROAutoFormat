# Контекст разработки (читать первым)

Это главная память проекта для любого ИИ-агента и для человека, продолжающего
работу. Файл описывает, что за программа, по каким правилам она сделана,
как она развёрнута и на какие грабли уже наступали.

## 0. Правило работы с этим файлом

1. **Сначала чтение.** Перед любой правкой кода агент обязан прочитать
   `agents_context.md` целиком и сверить свой план с разделами 1–9.
2. **Противоречия решаются в пользу кода.** Если файл расходится с кодом —
   прав код, а файл надо сразу исправить в том же коммите.
3. **После работы — запись.** Каждое изменение, которое затрагивает
   поведение программы, структуру файлов, настройки, развёртывание или
   внешние сервисы, обязано попасть в этот файл **в том же коммите**,
   что и само изменение. Коммит без обновлённого контекста считается
   незаконченным.
4. **Грабли записываем.** Любая найденная причина ошибки идёт в
   раздел 8, чтобы следующий агент не искал её заново.
5. **Коротко и без воды.** Файл — справка, а не журнал переписки.
   Устаревшие строки удаляем, а не накапливаем.
6. **Секретов здесь нет.** Никогда не записывать ключи API, токены,
   пароли, адреса туннелей и данные сверок.

## 1. Постоянные требования владельца

Эти правила нельзя нарушать без прямого разрешения:

- **Все настройки задаются через интерфейс программы**, включая ключи API
  и пароли почтового ящика. Никаких настроек только из файлов или
  переменных окружения. Исключение — программа-компаньон на рабочем
  компьютере: у неё своё окно настроек (раздел 5д).
- **`.env` не используется** как способ настройки функций. Сохранённые
  значения ложатся в `runtime.json` (см. раздел 4).
- **Коммиты идут прямо в `main`**, без промежуточных веток и PR.
- **Язык общения и интерфейса — русский.** Сообщения об ошибках
  должны быть понятны ревизору, а не программисту.
- **Сервисы, недоступные из России, по общему правилу не применять.**
  Прямые Google Gemini и OpenAI отклонены. Действующий провайдер
  зрения — **GigaChat (Сбер)**.
- **Исключение от 14.09.2026 (разрешение владельца):** **OpenRouter**
  разрешён для двух задач второго слоя проверки пересортов —
  **эмбеддинги имён** и **LLM-судья** (`verify_mode=llm`). Оба режима по
  умолчанию выключены: провайдер векторов по умолчанию — локальный файл
  ONNX, режим проверки по умолчанию — `off`, влияние логики — 100%.
  Распознавание фото это исключение не затрагивает: там остаётся GigaChat.
  Доступность и оплата OpenRouter из РФ — на стороне владельца.
- **ИИ здесь — подсказчик, а не решающее звено.** Любое распознавание
  товара или решение по пересорту подтверждает человек. Режим с нулевым
  влиянием логики — инструмент проверки качества моделей, а не способ
  отдать разбор машине: спорные пары всё равно подтверждает человек.
- **Выгрузка готовой сверки на рабочий компьютер идёт только по кнопке
  человека** на странице сверки, после всех подтверждений. Заливка
  входящего файла из папки может быть автоматической (раздел 5д).

## 2. Что делает программа

`ExcelKROAutoFormat` — веб-приложение (FastAPI + Jinja2) для обработки
файлов сверки инвентаризации из 1С. Пользователь загружает Excel-файл,
программа ищет пересорты (один товар в плюсе, похожий — в минусе),
предлагает решения, человек их подтверждает, на выходе — оформленный
файл с раскраской и рамками по правилам бухгалтерии.

Разделы интерфейса: сверка (`/`), зрение (`/vision`), почта ревизоров
(`/mail`), справочники (`/refs`), обучение (`/training`), обновление
(`/update`).

Рядом с веб-приложением есть **программа-компаньон** для рабочего
компьютера (пакет `companion/`): она заливает сверки из папки на сервер и
раскладывает готовый файл и архив снимков по папкам — см. раздел 5д и
`docs/13-companion.md`.

### Правила предметной области (менять только по просьбе)

Столбцы файла сверки:

| Столбец | Содержимое |
| --- | --- |
| A | код |
| B | наименование |
| C | характеристика (метка `не+` для излишка) |
| D | учёт |
| E | факт |
| F | итого, шт. |
| G | цена |
| H | сумма |
| I | сумма по учёту |
| J | разница сумм |
| K | документ движения |
| L (12) | служебный комментарий, сюда же пишется «нет фото» |

- Излишек никогда не идёт в плюс по сумме: `J = 0`.
- Пересорт: рамка `medium` цвета `FF000000` вокруг ячейки `F`.
- Неполный пересорт и недостача: заливка `FFFF00`.
- Излишек: заливка `FFC000` и метка `не+` в столбце C.
- Порог схожести для авторешения — 0,80; полоса сомнения — 0,70–0,90
  (такие строки уходят на ручную сверку).
- Плюсующая строка (`F > 0`) без подтверждённого фото получает в столбце L
  комментарий «нет фото». Отмечается именно отсутствие фото, а не наличие.

Монолитного `app/main.py` больше нет: маршруты разнесены по роутерам,
память процесса — в `app/state`, долгая работа — в `app/services`.

  config.py            базовые настройки (Settings, load())
  security.py          Basic-авторизация и проверка источника запроса
  state/
    jobs.py            разобранные сверки в памяти (Job, JobStore)
    letters.py         письма последнего захода в ящик
    exports.py         очередь выгрузок для компаньона (Export, ExportStore)
  services/
    upload_job.py      фоновый разбор сверки и пересборка файла (rebuild)
    letters.py         связка писем со сверкой для страниц
    photos.py          снимки и пометки «нет фото»
    samples.py         сохранение ответов человека в примеры
    exports.py         архив снимков задания (photo_zip, archive_name)
  web/

    messages.py        общие тексты ошибок
    routers/           upload, result, vision, mail, refs, training, update,
                       companion (машинные маршруты); ROUTERS в __init__.py
  core/
    runtime.py         настройки, заданные через интерфейс (runtime.json)
    pipeline.py        полный разбор файла сверки
    progress.py        ход разбора сверки: билеты, этапы, проценты
    resort.py          схожесть, группы, решения по пересортам (слой 1)
    verify.py          второй слой: логистическая регрессия, общий Verdict
    judge.py           второй слой: LLM через OpenRouter (LlmJudge)
    embed.py           эмбеддинги имён: провайдеры local и openrouter
    learning.py        примеры и обучение модели
    report.py          строки и сводка для страниц результата
    vision.py          распознавание фото через GigaChat
    mail.py            приём писем ревизоров по IMAP (фото и подсказки)
    mail_store.py      список писем на диске (mail-letters.json)
    mail_match.py      связка письма со сверкой по названию магазина
    mail_vision.py     разбор снимков писем при обработке сверки

Состояние живёт в памяти процесса и собрано в объектах `app/deps.py`:

- `jobs` (`state/jobs.py`) — разобранные сверки по токену. Один `Job` держит
  результат разбора, флаг `strict`, режим `verify`, влияние логики `logic`,
  снимки `photos`, строки с подтверждённым фото `photo_rows` и отчёт
  `mail_vision`. Свойство `alive` учитывает срок `RESULT_TTL_MINUTES`,
  свойство `warehouse` — название склада из шапки.
- `letters` (`state/letters.py`) — письма последнего захода в ящик; ящик один
  на службу, токена сверки там нет.
- `exports` (`state/exports.py`) — очередь выгрузок на рабочий компьютер.

Перезапуск службы стирает это состояние — об этом всегда предупреждаем
пользователя на странице обновления.

Ход разбора сверки хранит модуль `progress` в своей памяти: билетов не
больше 20 (`LIMIT`) и не дольше часа (`KEEP_SECONDS`), этап дольше
`SLOW_SECONDS` (180 с) подсвечивается. После перезапуска страница хода
честно отвечает «разбор не найден» и просит загрузить файл заново —
Internal server error там быть не должно.

### Охрана доступа (`app/security.py`)

- Приложение стоит за туннелем, поэтому ASGI-прослойка `SecurityMiddleware`
  требует Basic-авторизацию, если `app_host` не локальный
  (`127.0.0.1`, `localhost`, `::1`). Логин и пароль — `web_auth_user` и
  `web_auth_password`, сравнение через `hmac.compare_digest`.
- Единственный публичный путь — `GET /health` (`SAFE_PUBLIC_PATHS`), ответ
  `{"status": "ok", "version": …}`. Им пользуется кнопка «Проверить связь»
  в компаньоне.
- У изменяющих запросов сверяется источник: `Origin`/`Referer` должны
  совпадать с `Host`. **Отсутствие этих заголовков разрешено** — именно так
  работает компаньон и любой другой не-браузерный клиент. Неверный
  источник — 403 «Запрос заблокирован: неверный источник.»

## 4. Настройки и запись на диск

- Всё, что задал пользователь, хранит `app/core/runtime.py` в `runtime.json`.
- Путь по умолчанию `data/runtime.json`. Если папка недоступна для
  записи (так бывает при `ProtectSystem=strict`), перебираются запасные:
  `STATE_DIRECTORY` → `/var/lib/excelkro/data` → временная папка.
- Новые настройки добавляем так: значение по умолчанию в модуле,
  поле в шаблоне, сохранение через `runtime`. Никаких ручных правок
  файлов на сервере.
- Настройки зрения — `vision_*` (см. раздел 5), настройки эмбеддингов —
  `embed_enabled`, `embed_provider` (`local` или `openrouter`), `embed_api_key`,
  `embed_model`, `embed_api_url`, `embed_timeout`, `embed_retries`,
  `embed_max_requests` (см. `runtime.EMBED_FIELDS`, страница `/training`).
- Настройки LLM-судьи — `judge_api_key`, `judge_model`, `judge_api_url`,
  `judge_timeout`, `judge_retries`, `judge_max_requests`, `judge_batch`,
  `judge_max_pairs` и `logic_weight` (см. `runtime.JUDGE_FIELDS`, там же
  на `/training`). `runtime.FIELDS = EMBED_FIELDS + JUDGE_FIELDS`.
- Настройки почты — `mail_*` (см. раздел 5в). Они лежат в том же
  `runtime.json`, но перечислены в `mail.DEFAULTS`/`mail.KINDS`, а не в
  `runtime.FIELDS`: на `Settings` они не накладываются, модуль читает их сам.
- Ключи, токены и пароли вводятся только в интерфейсе и никогда не
  показываются целиком: только хвост (`vision.mask_key`, `embed.mask_key`,
  `mail.mask_secret`). Пустое поле ключа или пароля в форме значит
  «оставить как было»; есть отдельные кнопки удаления.
- Ключи эмбеддингов и LLM из окружения не читаются намеренно: только
  интерфейс и `runtime.json`.
- Настройки самого сервера (адрес, логин и пароль доступа, срок жизни
  сверки `RESULT_TTL_MINUTES`, предел загрузки `MAX_UPLOAD_MB`) — это
  `Settings` из `app/config.py`: их задаёт администратор при развёртывании,
  а не ревизор в интерфейсе.

## 5. Зрение: распознавание фото (GigaChat)

Задача: ревизоры присылают фото плюсующего товара; программа подсказывает,
какой строке сверки фото соответствует, человек подтверждает.

- Модуль `app/core/vision.py`, класс `GigaChatVision`.
- OAuth: `POST https://ngw.devices.sberbank.ru:9443/api/v2/oauth` с заголовками
  `Authorization: Basic <ключ>`, `RqUID: uuid4`, тело `scope=...`.
  Области: `GIGACHAT_API_PERS`, `GIGACHAT_API_B2B`, `GIGACHAT_API_CORP` —
  перебираются по очереди, так как тип ключа заранее неизвестен.
- Работа: `POST /api/v1/files` (multipart, `purpose=general`) → `id`, затем
  `POST /api/v1/chat/completions` с `messages[].attachments`, потом
  `POST /api/v1/files/{id}/delete`.
- Снимки уходят по одному, между запросами пауза (`vision_pause_seconds`),
  есть ограничения на размер фото и число строк подсказки.
- Подтверждение фото сбрасывает **только этот снимок**; остальные
  результаты остаются на странице (`job.photos`).
- **Снимки из писем ревизоров разбираются автоматически при обработке
  сверки** (`app/core/mail_vision.py`, вызов из `services/upload_job.py`):
  ответы модели попадают в `job.photos` и видны на `/vision`, а снимкам
  письма проставляется имя узнанного товара. Итог разбора показывается
  строкой сообщения на странице сверки. В модель уходят только письма
  своего магазина (см. раздел 5в).
- В файл сверки пишется пометка «нет фото»: её получают все плюсующие строки
  (`F > 0`) без подтверждённого снимка. Если в столбце 12 уже есть текст,
  пометка дописывается через запятую (`photo_mark.apply()`). Подтверждение
  снимка добавляет строку в `job.photo_rows` и снимает с неё пометку.
- Пометки ставятся **после каждой сборки файла** (`services/photos.py`,
  вызов из `services/upload_job.py`), потому что пересборка от исходника
  пишет столбец 12 заново.
- Запасные варианты, если GigaChat не устроит: локальный OCR
  (RapidOCR/PaddleOCR ONNX), Yandex Vision OCR, OpenRouter с Qwen-VL.

## 5а. Эмбеддинги имён (local или OpenRouter)

Подробно — `docs/07-ml-verifier.md`. Кратко:

- Модуль `app/core/embed.py`: `PROVIDERS = ("local", "openrouter")`,
  общий `BaseEmbedder` с дисковым кэшем, `OnnxEmbedder` и `RemoteEmbedder`.
- Сеть в серверном коде — только `urllib` из стандартной библиотеки: в
  `requirements.txt` нет `httpx`/`requests`. `httpx` разрешён только
  программе-компаньону (`requirements-companion.txt`).
- Адрес сетевого провайдера: `POST https://openrouter.ai/api/v1/embeddings`,
  тело `{"model": …, "input": […]}`, ответ `data[].embedding`.
  Модель по умолчанию — `qwen/qwen3-embedding-0.6b`.
- На пару имён — один запрос; `embed_max_requests` ограничивает траты
  на процесс (`EmbedLimit`), после чего сверка идёт без эмбеддингов.
- Любая ошибка эмбеддера — молчаливый отказ: `Verifier._embed_cos`
  ловит исключение и работает без признака.
- Маршруты: `POST /training/embed` (сохранить, редирект 303),
  `POST /training/embed/check`, `POST /training/embed/key/clear`.
- Признаки `embed_cos`/`embed_known` получают веса только после
  переобучения модели на `/training`.

## 5б. LLM-судья и влияние логики

Подробно — `docs/07-ml-verifier.md`. Кратко:

- Режимы второго слоя: `verify_mode` = `off` (только логика), `model`
  (логистическая регрессия), `llm` (языковая модель). «LLM в связке с
  эмбеддингами» — это режим `llm` при включённых эмбеддингах: косинус
  близости имён уходит в текст подсказки.
- Модуль `app/core/judge.py`, класс `LlmJudge`: запрос
  `POST https://openrouter.ai/api/v1/chat/completions` через `urllib`,
  модель по умолчанию `openai/gpt-4o-mini`, ответ строго
  `{"answers": [{"id": 1, "p": 0.9}]}`.
- `Verdict` из `verify.py` получил поле `known`. `known=False` значит
  «ответа нет» (сеть, ключ, предел): пару решает логика, а пара, не
  прошедшая ворота, отбрасывается.
- Ответы кэшируются по нормализованным именам пары (`plus.key=>minus.key`),
  а не по номерам строк: пересборка файла новых трат почти не даёт.
  Предел пар (`judge_max_pairs`) считается на файл, предел запросов
  (`judge_max_requests`) — на процесс. Пары идут пачками (`judge_batch`),
  лучшие кандидаты слоя 1 — первыми.
- `logic_weight` (0…1, в интерфейсе 0…100% на странице загрузки) действует
  только при включённом втором слое. 100% — прежнее поведение (жёсткие
  ворота, `score + verdict.bonus`). Меньше 100% — ворота мягкие
  (кандидатами становятся все пары плюс×минус), итог считает
  `resort.mixed_score`: `w * логика + (1 - w) * 2 * порог * шанс модели`.
  При 0% решает только модель. Без второго слоя вес игнорируется и
  пишется строка в журнал.
- Маршруты: `POST /training/judge` (сохранить, редирект 303),
  `POST /training/judge/check` (пробная пара Мальборо/Marlboro),
  `POST /training/judge/key/clear`. Поля формы: `api_key`, `model`,
  `api_url`, `timeout`, `retries`, `batch`, `max_pairs`, `max_requests`,
  `logic`.
- Влияние логики на один файл передаётся полем `logic` формы `/upload`
  и запоминается в `Job.logic`; при пересборке значение берётся из памяти.

## 5в. Почта ревизоров (IMAP)

Подробно — `docs/11-mail.md`. Кратко:

- Модуль `app/core/mail.py`, страница `/mail`, шаблон `templates/mail.html`.
- Только стандартная библиотека: `imaplib` и `email`, новых зависимостей
  нет. Mail.ru и Яндекс доступны из России, вход — по **паролю
  приложения** ящика, без OAuth.
- Настройки: `mail_enabled`, `mail_host` (по умолчанию `imap.mail.ru`),
  `mail_port`, `mail_login`, `mail_password`, `mail_folder`, `mail_senders`
  (белый список, можно доменом `@firma.ru`; пусто — принимать всех),
  `mail_only_unseen`, `mail_since_days`, `mail_max_letters`,
  `mail_max_photos`, `mail_max_photo_mb`, `mail_timeout`, `mail_mark_seen`,
  `mail_keep_days`.
- **Имя папки кодируется в modified UTF-7 (RFC 3501)** и берётся в
  кавычки: `mail.encode_folder`, `mail.decode_folder`, `mail.quote_folder`.
  Без этого `imaplib` падает на кириллице («Отчёты») ещё до отправки
  команды. Если папка не найдена, в ошибку кладётся список настоящих имён
  папок (`mail.list_folders`, функция `mail.folders`).
- Письма забираются **только по кнопке**: состояние сверок живёт в памяти
  процесса, фоновому сбору некуда складывать результат.
- Номера разобранных писем хранятся в `mail-state.json` (последние 1000):
  флаг «прочитано» ненадёжен, ящик смотрит и человек. Снимки лежат в
  `mail-photos/<uid>/NN-имя.jpg` и удаляются по `mail_keep_days` при
  каждом заходе.
- Из текста берутся только детерминированные подсказки
  (`mail.read_hints`): коды товара, количество, магазин, слова письма.
  Никакой модели на этом шаге нет.
- `mail.check()` наружу отдаёт только пару «получилось, что сказать
  человеку»: любая неожиданная ошибка тоже превращается в текст, чтобы
  страница не падала с Internal server error.
- Маршруты: `GET /mail`, `POST /mail/settings` (редирект 303),
  `POST /mail/check`, `POST /mail/fetch`, `POST /mail/parse/{uid}`,
  `POST /mail/clear`, `POST /mail/password/clear`,
  `GET /mail/photo/{uid}/{name}`, `GET /mail/archive/{uid}?token=…`.
  Имена вложений чистит `mail.safe_name`, а путь отдаваемого снимка
  дополнительно сверяется с папкой снимков.
- **Связка письма со сверкой по названию магазина — `app/core/mail_match.py`.**
  Ящик один на службу, поэтому **до любой отправки снимков в нейросеть**
  письма делятся на свои и чужие: склад сверки (`job.warehouse`, например
  «ВыборгРебусПДВ») сравнивается с темой письма и подсказкой
  `hints["store"]`. Названия нормализуются (нижний регистр, «ё»→«е»,
  разбивка слитного названия по заглавным буквам), служебные слова темы
  («магазин», «сверка», «фото», «излишки» и подобные) не считаются
  названием; совпадением считается одинаковое слово, вхождение слова
  длиной от `MIN_PART` (4) букв или схожесть от `MIN_RATIO` (0,82) по
  `difflib`. Точка входа — `mail_match.split(warehouse, items)` →
  `{"mine", "others", "note"}` и `mail_match.fits`; в веб-слое это
  `services/letters.py`.
  Следствия: в GigaChat уходят только снимки своих писем, на странице
  готовой сверки видны только их кнопки архивов, подсказки формы (товар в
  списке несосчитанного, ФИО продавца) берутся из писем того же магазина.
  Совпадений нет — запросов к модели не делается вовсе, а причина пишется
  текстом (`mail_match.NO_MATCH`). Ручная кнопка «Отправить на разбор»
  связкой не ограничена (письмо и сверку выбрал человек), но при
  несовпадении магазина рядом с итогом пишется предупреждение.
- **Разбор снимков писем — `app/core/mail_vision.py`.** При обработке
  сверки (а при пересборке — только если разбора ещё не было) снимки
  связанных писем уходят в `vision.recognize_all` с излишками этой сверки:
  каждому снимку ставится имя узнанного товара (`Photo.title`), ответы
  модели добавляются в `job.photos`, отчёт лежит в `job.mail_vision`. Нет
  ключа, выключено распознавание, нет излишков или связанных писем —
  снимки остаются со своими именами, а причина пишется в сообщении
  страницы (`mail_vision.summary`).
- **Разбор снимков писем ограничен**: письма, где все снимки уже названы,
  пропускаются (`only_new=True`), а за один заход разбирается не больше
  `mail_vision.LIMIT` (12) снимков. Без этого каждая сверка гоняла бы в
  модель весь накопленный архив — это и была причина «бесконечной
  загрузки» (см. раздел 8). Кнопка «Отправить на разбор» снимает оба
  предела (`only_new=False`, `limit=0`).
- Тесты — `tests/test_mail.py`, `tests/test_mail_match.py`,
  `tests/test_mail_store.py` и `tests/test_mail_vision.py`, без сети:
  ящик подменяется через аргумент `opener` у `check()` и `collect()`,
  распознавание — через аргумент `recognizer` у `recognize_letters()`.

## 5г. Ход разбора сверки

Подробно — `docs/12-progress.md`. Кратко:

- `POST /upload` только сохраняет файлы, заводит билет (`progress.start`)
  и отвечает редиректом 303 на `/upload/progress/{билет}`. Сам разбор
  идёт фоновой задачей (`services/upload_job.py`).
- Этапы задаёт веб-слой (`UPLOAD_STAGES`): «Файл принят» → «Разбор
  сверки» → «Пометки „нет фото“» → «Снимки из писем». Порядок важен:
  проценты полосы считаются как доля закрытых этапов.
- Как только файл собран, сверка кладётся в память (`jobs.remember`) и
  доступна по `/result/{токен}`, не дожидаясь необязательных шагов;
  страница хода в этот момент уже даёт на неё ссылку, а по концу уводит
  туда сама (редирект 303 из `/upload/progress/{билет}`).
- Страница обновляется сама (meta refresh 2 с, адрес свой же, поэтому без
  `url=`): полоса, текущий этап, время каждого шага.
  `GET /upload/state/{билет}` отдаёт то же самое в JSON.
- Ошибка разбора становится текстом на главной странице (`progress.fail`),
  сбой необязательного этапа не роняет сверку (`progress.stage_failed`).
- Шаблон `templates/progress.html` служебный: в меню `nav_items` он не
  добавляется, на него ведёт только редирект из загрузки.
- Тесты — `tests/test_progress.py` (модуль) и сценарии загрузки в
  `tests/test_web.py`: там разбор дожидаются опросом
  `/upload/state/{билет}`.

## 5д. Программа-компаньон и машинные маршруты

Подробно — `docs/13-companion.md`. Задача: сервер стоит за туннелем и сам
до рабочего компьютера и сетевой папки `\\termserver\office\КРО_03\ОБЩАЯ`
не достучится, поэтому файлы носит программа на рабочем компьютере.

Порядок работы, который выбрал владелец:

1. Компаньон следит за папкой «входящие», ждёт, пока файл перестанет
   меняться, и заливает его на сервер.
2. Сверка появляется в разборе, человек в браузере подтверждает пары,
   заявки и шапку.
3. Человек нажимает на странице сверки **«Выгрузить на компьютер»**.
4. Компаньон забирает готовый файл и архив снимков и кладёт их в папку
   «исходящие». Сам он ничего не выгружает.

- Пакет `companion/`: `config.py` (настройки и папки), `state.py` (журнал
  заданий `companion-jobs.json`), `client.py` (`Client`, `ServerError`,
  `Gone`), `worker.py` (`Companion.tick`: заливка, слежение, выгрузка),
  `ui.py` (окно настроек и значок в трее), `__main__.py` (ключи `--раз`,
  `--без-трея`, `--настройки`).
- Настройки компаньона лежат в `%LOCALAPPDATA%\ExcelKRO`
  (`companion-state.json`, `companion-jobs.json`, `companion.log`) и
  задаются в своём окне: адрес сервера, логин и пароль доступа, папки
  «входящие», «исходящие», «ошибки», «архив», сроки опроса и ожидания,
  режимы сверки (`strict`, `verify`, `logic`), прошлая сверка из архива.
- Зависимости компаньона — отдельный файл `requirements-companion.txt`
  (`httpx`, `pystray`, `pillow`). В серверный `requirements.txt` они не
  попадают.
- Очередь выгрузок — `app/state/exports.py`: статусы «ждёт», «забирается»,
  «выгружено», «сбой», не больше `LIMIT` (50) записей, живут `KEEP_SECONDS`
  (сутки). Кнопка на странице сверки ставит запись (`exports.request`),
  вторая кнопка её снимает (`exports.forget`).
- Архив снимков задания — `app/services/exports.py`: имя
  `Фото_<склад>_<дата>.zip`, сначала пишется `*.zip.part`, потом
  `replace` — компаньон не заберёт недописанный файл.
- Машинные маршруты (`app/web/routers/companion.py`, префикс
  `/api/companion`, та же Basic-авторизация):
  `POST /jobs` (залить сверку, ответ с билетом), `GET /jobs/{ticket}`
  (ход разбора и токен), `GET /exports` (что ждёт выгрузки),
  `GET /exports/{token}/result` (готовый файл),
  `GET /exports/{token}/photos.zip` (архив снимков),
  `POST /exports/{token}/done`, `POST /exports/{token}/failed`.
- Страница сверки: раздел «Выгрузка на рабочий компьютер» с кнопками
  «Выгрузить на компьютер» (`POST /export/{token}`) и «Отменить выгрузку»
  (`POST /export/{token}/cancel`), состояние приходит в контексте как
  `export` (`render.export_state`).
- Тесты — `tests/test_exports.py` (очередь и архив снимков) и
  `tests/test_companion.py` (заливка, слежение, выгрузка; сервер
  подменяется `FakeClient`, сети в тестах нет).

## 6. Развёртывание и обновление

Сервер владельца: VPS, папка `/opt/excelkro`, состояние в `/var/lib/excelkro`,
служба `excelkro`. **Служба запущена от root**, не от пользователя
`excelkro`, потому что развёртывание было ручным, без `deploy/install.sh`.
Любой код и скрипт должен работать в обоих случаях.

Обновление по кнопке (OTA):

- Страница `/update`, модуль `app/core/update.py`, скрипт `deploy/ota-update.sh`,
  шаблон unit `deploy/excelkro-update@.service`, доустановка
  `deploy/install-ota.sh`, правило `deploy/sudoers-excelkro`.
- Работа идёт в отдельной службе `excelkro-update@<режим>`, чтобы
  перезапуск приложения не обрывал само обновление. Режимы: `check`
  и `apply`.
- **Unit запускает скрипт через `bash`** (`ExecStart=/bin/bash …/ota-update.sh %i`):
  `git reset --hard` во время обновления возвращает файлам права из
  репозитория и снимает флаг `+x`. Поэтому `parts()` право запуска
  не проверяет, а скрипт после обновления сам делает `chmod +x deploy/*.sh`
  и переставляет описание службы обновления (только при стандартных путях).
- `update.parts()` проверяет наличие unit-файла, скрипта и правила sudo и
  перечисляет недостающие части. Под root правило sudo не нужно
  (`as_root()`), в этом случае `start()` вызывает `systemctl` напрямую.
- Состояние обновления — `update-state.json`, журнал — `update.log`
  в папке состояния.
- Страница обновляется сама, пока `status.busy`; в теге автообновления
  обязателен явный `url=/update`.
- **Остановка службы может затянуться**, если в это время идёт фоновый
  разбор снимков через GigaChat: uvicorn ждёт закрытия соединений и
  служба висит в `deactivating (stop-sigterm)`. Быстрое лечение —
  `systemctl kill -s SIGKILL excelkro && systemctl start excelkro`.
  Постоянное лечение (отложено, раздел 9): отмена фоновых задач при
  остановке и `TimeoutStopSec=20…30` в unit-файле.
- Команды на сервере:

```
cd /opt/excelkro && git pull --ff-only
bash deploy/install-ota.sh
systemctl restart excelkro
systemctl show -p User -p ExecStart --value excelkro
```

## 7. Правила разработки

- Шаблоны — Jinja2 без фронтенд-сборки, наследование от `base.html`.
  Новый раздел добавляется двумя шагами: шаблон и запись в `nav_items`
  внутри `base.html`. Служебные страницы без своего раздела
  (`progress.html`) в `nav_items` не добавляются.
- Новый маршрут живёт в своём роутере `app/web/routers/*` и
  подключается через `ROUTERS` в `routers/__init__.py`. Общая память и
  зависимости берутся из `app/deps.py`, а не создаются заново.
- Действия — POST-формы; при показе страницы после действия лучше
  редирект 303 (образец — `/training`). Если на странице нужно показать
  результат действия, страница рисуется сразу, без редиректа.
- **Скрытые поля `token` в формах обязательны**, иначе запись в файл
  молча не происходит. Это касается форм, работающих с конкретной
  сверкой; у раздела почты токена нет — ящик один на службу.
- Долгая работа (разбор файла, сеть, почта) уходит в отдельный поток:
  либо синхронный обработчик, который FastAPI сам уносит в пул, либо
  `run_in_threadpool`. Внутри `async def` блокирующий код вызывать нельзя.
  Дольше одного запроса работу ведёт фоновая задача, а человек смотрит
  ход работы на странице с билетом (см. раздел 5г).
- **Запросы к внешним моделям делаем только по делу.** Перед отправкой
  снимков в нейросеть данные должны быть связаны детерминированно.
- Сообщения об ошибках конкретные и на русском: что случилось и что делать.
  Обработчик страницы не должен падать с Internal server error: ошибку
  внешней службы превращаем в текст на странице.
- Правки желательно закрывать тестами в `tests/` (pytest).
- Документация: `docs/07-ml-verifier.md` — второй слой, эмбеддинги и LLM,
  `docs/09-ota-update.md` — обновление, `docs/10-photo-vision.md` — зрение,
  `docs/11-mail.md` — почта ревизоров, `docs/12-progress.md` — ход разбора,
  `docs/13-companion.md` — программа-компаньон. Обновляется вместе с кодом.
- **Права файлов в репозитории ненадёжны.** Не опираться на флаг `+x`:
  скрипты запускать явно через `bash …`.

## 8. Грабли (симптом → причина)

| Симптом | Причина и решение |
| --- | --- |
| Не пишется файл в `/opt/excelkro/data` | `ProtectSystem=strict` в unit-файле. Решение: перебор запасных папок в `runtime.py`. |
| Ответы модели пропадали после подтверждения одного фото | Хранился один результат на токен. Решение: снимки лежат в `Job.photos`, сбрасывается только нажатый снимок. |
| «Служба обновления не запускается» | Не доустановлены части OTA. Решение: проверка `parts()` с перечнем недостающих частей. |
| «Нет пользователя excelkro» в `install-ota.sh` | Служба работает от root. Решение: скрипт определяет пользователя службы сам. |
| «Не хватает правила sudo» при работе от root | Под root sudo не нужен. Решение: `as_root()` и прямой вызов `systemctl`. |
| `{"detail":"Method Not Allowed"}` после кнопок обновления | Тег автообновления без `url=`. Решение: всегда `url=/update`. |
| Комментарии по фото не попадают в сверку | Пометка ставилась один раз при подтверждении, а любая пересборка файла от исходника (в том числе `claims.apply`) её стирала. Решение: строки хранятся в `Job.photo_rows`, а `photo_mark.apply()` вызывается после каждой сборки файла. |
| Снимки письма уходили в GigaChat при каждом скачивании архива | Имена товару проставлялись в обработчике архива, поэтому каждое нажатие тратило запросы заново. Решение: разбор идёт один раз при обработке сверки, а названные снимки пропускаются. |
| После каждого обновления страница снова пишет «не хватает права запуска у deploy/ota-update.sh» | `git reset --hard` возвращает права из репозитория и стирает `chmod 755`. Решение: unit запускает скрипт через `/bin/bash`, `parts()` право запуска не требует, а `ota-update.sh` сам возвращает `+x`. |
| После смены провайдера эмбеддингов первая сверка идёт медленнее | Ключ дискового кэша содержит провайдера и модель, старые записи не подходят. Это ожидаемо и безвредно. |
| Сверка с влиянием логики меньше 100% идёт заметно дольше | При мягких воротах оценка считается для всех пар плюс×минус внутри группы. Это цена режима: на больших складах держать 100% или ограничивать `judge_max_pairs`. |
| В режиме `llm` часть пар решена логикой, хотя ключ задан | Исчерпан предел пар на файл или запросов на процесс, либо сервис не ответил: пара получает `known=False`. Причина — в `LlmJudge.last_error` и в журнале службы. |
| Пункт меню «Почта ревизоров» отвечал 404 | Шаблон и пункт меню были закоммичены раньше маршрутов. Решение: новый раздел без обработчика не коммитить. |
| Ссылка на снимок из письма не открывалась | На диске файл лежит с номером по порядку (`01-photo.jpg`), а в письме у вложения своё имя. Решение: поиск и по полному имени, и по части после первого дефиса. |
| Белый список адресов ревизоров нельзя было очистить | Пустое текстовое поле в `save_config` означает «оставить как было». Решение: `POST /mail/settings` записывает пустой `mail_senders` принудительно. |
| «Ящик не пускает» при верном пароле | Введён основной пароль учётной записи. Нужен отдельный **пароль приложения** ящика, а в Mail.ru — ещё и включённый доступ по IMAP. |
| Проверка почты давала Internal server error для папки «Отчёты» | Имена папок в IMAP передаются в modified UTF-7 (RFC 3501), `imaplib` падал с `UnicodeEncodeError`. Решение: `mail.quote_folder()`, `_select` ловит `UnicodeError`, `check()` превращает любую ошибку в текст. |
| «Папка не найдена», хотя в почте она видна | Для сервера важны регистр и буква «ё»; вложенная папка пишется как `INBOX/Отчёты`. Решение: в сообщение добавлен список настоящих имён папок. |
| Разбор сверки выглядел бесконечной загрузкой | `POST /upload` отвечал только после всех шагов, а последним шёл разбор снимков писем. Решение: разбор ушёл в фоновую задачу со страницей хода работы, а названные снимки пропускаются (`only_new`, `LIMIT`). |
| Тесты загрузки падали после ухода разбора в фон | Ответ на `POST /upload` — редирект на страницу хода. Решение: тесты дожидаются конца разбора опросом `/upload/state/{билет}`. |
| Служба зависла в `deactivating (stop-sigterm)` после обновления | Фоновая задача разбора снимков держала GigaChat, uvicorn ждал закрытия соединений. Лечение: `systemctl kill -s SIGKILL excelkro`, затем `systemctl start excelkro`. Постоянное решение отложено (раздел 9). |
| Сверка предлагала архивы всех писем ящика и проверяла фото чужого магазина | Письма никак не связывались со сверкой. Решение: `app/core/mail_match.py` связывает письмо со сверкой по названию магазина **до** отправки снимков в нейросеть. |
| Компаньон получал 403 «неверный источник» | Прослойка охраны сверяла `Origin`/`Referer` с `Host`. Не-браузерный клиент их не посылает, поэтому **отсутствие заголовков считается разрешённым**; компаньон их не подставляет намеренно. |
| Компаньон забирал недописанные файлы | Архив снимков и файл сверки пишутся во временное имя (`*.zip.part`) и переименовываются через `replace`; входящий файл из папки берётся только после того, как размер и время не менялись `stable_seconds`. |
| В инструменте `push_files` длинный файл ушёл обрезанным | Слишком большой вызов обрезается по середине содержимого. Решение: длинные файлы отправлять по одному в вызове и проверять конец файла после записи. Так же обрезается и `create_or_update_file`: кириллица в экранированном виде (`\u0430`) занимает в шесть раз больше места, чем обычный текст. |
| Поиск по коду в GitHub (`search_code`) ничего не находит | Индекс репозитория пуст. Решение: читать файлы напрямую (`get_file_contents`) и смотреть дерево ветки. |
